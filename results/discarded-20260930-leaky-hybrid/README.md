# 破棄した run — Arm C の絞り込みに抜け道があった

**この 2 つの run の数値を結論に使わないこと。**

| run | 規模 | 正答率（参考） |
|---|---|---|
| `p4-n150-hybrid` | 151 ファイル | 0.909 |
| `p4-n1000-hybrid` | 1,524 ファイル | 0.909 |

## 何が起きたか

Arm C は「ベクトル検索でファイルを N 件に絞り、その範囲だけをエージェントに渡す」
と定義されている（SPEC §4-2, §14-7）。実装は道具ごとに `ToolContext.allowed` で
弾く方式だったが、抜け道が 3 つあった。

1. `read_file` は `files/` 配下にしか制限を掛けておらず、**ミラー（`_index/mirror/`）を素通し**
2. `grep` はカタログの**全行**を返すので、候補外のファイル名が見える
3. `run_python` は任意のコードなので、**候補外の原本をどれでも開ける**

1,524 ファイルの run で、規模プローブでは候補にパスワード規則が 1 問も入らない
`locked` が正答率 1.00 だったことから発覚した。セッション記録を見ると、エージェントは
grep でカタログから `ST-2884_handling.docx` を見つけ、候補外のミラーを `read_file` で
読んでいた。

`read_file` / `view_image` の記録だけで数えても、候補外を開いた行は
151 ファイルで 1/66、1,524 ファイルで 9/66（うち `locked` 6）。
P3（311 ファイル）の `p3-hybrid-forced` でも 6/198（すべて `version`）あり、
**P3 の Arm C も同じ抜け道の上の数字**である。

## 対応

設問ごとに**候補ファイルだけをハードリンクした作業ディレクトリ**を作り、
エージェントにはそこだけを渡すよう改めた（`arms/hybrid/arm.py`、SPEC §14-9）。
候補外のファイルは物理的に存在しないので、どの道具でも届かない。
修正後に同じ `locked-03` を回すと、エージェントは zip を開けず囮（速報値）を答えた。

同じ run-id で測り直した結果が `results/p4-n150-hybrid` と `results/p4-n1000-hybrid` にある。
