> ❌ **結果を見てから採点基準を変えること**。`answer_aliases` は生成時に確定させ、
> 事後追加したら必ずレポートに明記する

このファイルは、その「明記」の場所である。**採点に影響しうる変更は、結果を見た
あとのものであれ前のものであれ、すべてここに時系列で記録する。**記録のない

## 2026-09-25 — 判定の安全弁: 囮に一致した回答を judge にかけない

**種別**: 採点ロジックの変更（結果を見る前に決めた原則。ただし実装は run 中）

**内容**: `Item.decoys` に一致した回答は、LLM judge の判定対象から外して
不正解のまま確定させる。

**理由**: 囮は**生成時に確定した誤答**である（例: 陳腐化したキャッシュ値
`28671500` に対し、正解は `28981700`）。judge がこれを正解と判定したら、
それは judge 側の誤りであって採点の揺れではない。桁の違う数値を正解にしないための
安全弁。

**この変更が結果に与えた影響**: 発動回数を `scoring_meta.json` の
`judge_blocked_on_decoy` に必ず記録する。**0 なら採点は 1 件も変わっていない。**
0 でない場合は、その件数ぶん classical の正答率が下がる方向に働くため、
レポートで必ず件数を開示すること。

**`p0-seed42-ja` での実績**: 42 件で発動した（囮の実体は 4 種類）。
件数が多いので、ガードが結果を歪めていないかを実際に検証した。
囮 4 種すべてを judge にかけたところ、**4/4 で judge も「不正解」と判定**した。

```
formula-09: 回答=32595200 正解=35937000 → 不正解（数値が正解と不一致）
formula-06: 回答=75322500 正解=79110900 → 不正解（数値が正解と不一致）
formula-03: 回答=28671500 正解=28981700 → 不正解（数値が正解と不一致）
formula-12: 回答=41781300 正解=43700800 → 不正解（数値が正解と不一致）
```

**したがってこのガードは 1 件も採点を変えていない。** classical の正答率を
不当に下げてはいない。

## 2026-09-25 — `text` チャネルの `site` に「〜構内」の alias を追加（次回コーパスから）

**種別**: `answer_aliases` の事後追加（★ 結果を見たあとの変更）

**発端**: `p0-seed42-ja` の run で `text` 難易度1 に 4 件の誤答が出た。中身を見ると
すべて同じ形だった。

```
設問: 案件コード PRJ-1455 の作業を実施する場所はどこか。
正解: 大阪支社   回答: 大阪支社構内
```

文書の作業範囲の節に「作業範囲は大阪支社**構内**に限る」とあり、モデルはそこから
答えている。場所としては同一で、表記の揺れに当たる。

**判断**:

1. **`p0-seed42-ja` の run には alias を足さない。** 実行中のコーパスの採点基準を
   途中で変えることになるため。この run はもともと SPEC §5-1 が用意している
   **LLM judge** で処理し、judge が exact を覆した件数を結果に明記する。
2. **生成器には alias を足す**（`gen/channels/text.py`）。「〜構内」は文書の文面から
   予測できる表記であり、本来は生成時に確定しておくべきものだった。
   **次回生成するコーパスから適用**する。

**影響**: alias 追加後のコーパスでは、`text` の正答率がこのぶん上がる。したがって
**alias 追加前後の run を直接比較してはいけない**。比較するときは `meta.json` の
`generator_version` が一致していることを確認すること。

## 2026-09-25 — 診断列の追加: 本文で棄権している回答の可視化（採点は変えない）

**種別**: 診断の追加（**採点ロジックは変更していない**）

**内容**: `abstained` が false のまま、本文で「抜粋からは算出不可」「情報不足」などと
答えている回答を数え、`scoring_meta.json` の
`textual_refusals_counted_as_answers` に記録する。

**理由**: 出力契約（SPEC §4-2）は `abstained` フラグを棄権の唯一の表現としている。
契約どおりフラグを正として採点するが、フラグを立てずに本文で棄権する回答があると、
それは `answered` かつ誤答として数えられ、`penalized` が実態より低く出る。
**採点を変えずに、読むときの交絡として開示する**ための列。

**採点への影響**: なし。件数を記録するだけ。0 でなければレポートで言及すること。
